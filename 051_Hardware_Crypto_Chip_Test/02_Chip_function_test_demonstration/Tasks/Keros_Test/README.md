# EEPROM 用户页与范围测试

包含 `keros_demo.h`，保持原来的初始化及两个测试入口，`main.c` 不由模块修改：

```c
keros_demo_status_t keros_demo_init(void);
keros_demo_status_t keros_demo_test(keros_demo_report_t *p_report);
keros_demo_status_t keros_demo_test_read_only(keros_demo_report_t *p_report);
```

先完成 HAL、系统时钟、外设和 EasyLogger 初始化，在中断开启的主循环
上下文调用。接口返回调用方，不创建任务或永久循环，不支持并发或 ISR 调用。
Keil 保留 `Bsp/Keros`、`Tasks/Keros_Test` 的头文件搜索路径、源文件和配套
静态库链接；无需将头文件加入 Manage Project Items。

## 当前范围与限制

本次使用新版 `pattern=v2`。请求库页号 **0～35**，每页 64 字节，逻辑请求
范围为 2304 字节，覆盖 2 KB 的候选范围以及边界外四页。

完整手册第 5 页说明 15 个用户块，第 11 页表 [6.1] 列出 30 个用户页。
手册页标签为 Page01～Page30；当前 SDK 的参数为零基页号 0～29。
因此可通过现有接口测试的用户数据是 **30 × 64 = 1920 字节**。
SDK 内部页范围和块范围检查不允许访问第 30 页起的请求。

| 库页号 | 逻辑字节偏移 | 请求意义 |
|---|---|---|
| 0～15 | 0～1023 | 第一个 1 KB 请求范围 |
| 16～29 | 1024～1919 | 其余已说明用户页 |
| 30～31 | 1920～2047 | 2 KB 候选范围内，当前库不支持 |
| 32～35 | 2048～2303 | 2 KB 边界外，当前库不支持 |

程序实际调用库尝试每一页，**不绕过库访问未说明的寄存器或存储区**。
当库返回 4/5/18、请求页号至少为 30、底层无错误且实际 I2C 次数为零时，
标记 `SDK_LIMIT`。这表示软件库拒绝请求，**不表示芯片在该地址拒绝访问**。
三份提供的资料没有给出其余 128 字节或 2 KB 外侧的 EEPROM 读写协议。
完整物理容量和边界探测仍需要厂家提供相应协议或支持该范围的库。

`KEROS_EEPROM_CAPACITY_BYTES` 原配置保留，但不参与跳过、限制或型号推断；
启动日志改为打印请求范围，避免把配置值当成实测容量。

## 两次测试

1. **先运行新版写读入口** `keros_demo_test(&report)`，保存完整日志。
   它先逐页尝试写入 0～35 页，再统一尝试读回 0～35 页。
2. 选择 `keros_demo_test_read_only(&report)`，重新编译并烧录。
3. 第二版烧录后让整板与被测芯片真正断电，再重新上电运行只读测试。
   确认调试器、USB 或信号线没有继续供电；以此次重新上电的日志为准。
4. 第二版只运行只读入口，不先运行写读测试或其他 EEPROM 写入代码。
5. 比较两份日志的序列号、`pattern=v2`、页号和每页完整的 `READ` 数据。

**写读模式覆盖全部可写用户页，包括页 0，原有业务数据不会恢复。**
本测试只调用普通 EEPROM 数据接口，不执行 eFuse、OTP 配置或密码修改。
只读模式不调用 EEPROM 写入；初始化、认证和读取仍会发送 I2C 控制命令。
不能用旧版三页 `pattern=v1` 的写入日志核对新版只读测试。

## 数据及执行方式

- 两种模式使用同一个按页生成的固定 v2 数据，不依赖第一次运行的 RAM。
- 每页前五字节为 `4B 52 02 <page> <page XOR FF>`；剩余字节按固定公式生成。
- 全部页均使用明文、密码 0，每页各尝试一次，便于统一比较容量和地址。
  原来第 2 页的加密 EEPROM 测试由范围测试替代；AES 加解密回环仍保留。
- 写入完成后才进行最终读回，可发现后续页写入覆盖前面页的现象。
- 实际读回完整匹配另一页模式时输出 `ALIAS_CANDIDATE pattern_page=...`，
  作为页地址重复的线索，不直接宣称已经确定物理映射。
- 每页写入、读取分别保存状态；写入失败仍读取该页，并继续后续页。
- 读缓冲区每次清零，期望数据与厂家工作缓冲区分开，比较全部 64 字节。

初始化读取序列号；测试依次执行 BYPASS、认证、AES 回环及存储范围测试。
BYPASS 失败跳过后五项，认证失败跳过后四项。AES 回环单独失败不阻止
页扫描。初始化失败时所有测试跳过。

## 日志与判定

启动日志标记 `WRITE_READ` 或 `READ_ONLY`，以及 `pattern=v2`。
写读入口随后输出 `phase=WRITE_ALL`，两种入口都输出 `phase=READ_ALL`。
每页打印零基页号、逻辑字节偏移、完整期望值，以及有效访问时的完整读回值。
64 字节分四行，行内偏移为 `00/10/20/30`。每行间隔 10 ms，减轻 RTT
缓冲区压力；测试开始前连接 RTT Viewer 并保存完整日志，缺行时不能作完整比对。

每页结果包括：

- `WRITE: COMMAND_OK`：写入库调用及底层检查通过，还不是存储保持确认。
- `READ: MATCH_UNVERIFIED`：实际读取且完整数据匹配，外部断电过程由操作者确认。
- `FAIL`：实际库错误、底层错误、没有传输的成功返回，或数据不匹配。
- `SDK_LIMIT (not a hardware boundary)`：库拒绝且没有底层传输，硬件范围未测到。
- `raw`、`reason`、`io_read`、`io_write`：库原始状态、原因及本次实际 I2C 次数。
- 失败时附带首个底层错误、子地址和方向，访问或数据失败保留“未识别到
  EEPROM 芯片”日志；该文字本身不证明硬件缺失。

最近两段完整写读与只读日志中，页 0～29 的 1920 字节均符合期望，
两轮读回逐字节一致，页 0 和页 23 本次也匹配。两轮均输出：

```text
EEPROM pages: requested=36 match=30 fail=0 sdk_limit=6
EEPROM matched_bytes=1920; physical_capacity=UNDETERMINED
Total=6 passed=3 failed=0 skipped=0 unverified=2 sdk_limit=1
```

六项汇总仍保留三个基础功能项；原来的三个 EEPROM 项现在对应请求页
0～15、16～31、32～35。混合范围同时显示匹配页数和库受限页数。
`matched_bytes` 表示本次有效匹配的数据量，**不是测定的物理容量**。

本次提供的日志还包含一段额外写读片段，其与实际断电时点的关系未确认。
因此目前记录为读回一致性通过；断电保持结论仍需确认完整断电且期间
没有重新写入。不能据此认定具体型号或丝印错误。

36 页是应用请求数量，不是芯片总页数；2 KB 为 2048 字节，按 64 字节
换算为 32 个单位，也不能证明存在 32 个用户可访问页。

## 返回值与报告

原有返回值保留。初始化成功为 `KEROS_DEMO_OK=0`；测试有实际失败或
前置跳过时返回 `KEROS_DEMO_TEST_FAILED=5`。无实际失败但请求受 SDK
限制时返回 `KEROS_DEMO_EEPROM_SDK_LIMIT=9`；全部请求匹配且没有库限制
时返回 `KEROS_DEMO_EEPROM_UNVERIFIED=8`。

`report.items[]` 是六个汇总项，保留原枚举名称及值。新增 `SDK_LIMIT=4`
结果状态和 `SDK_LIMIT=9`、`NO_TRANSFER=10` 原因。总数满足
`passed + failed + skipped + unverified + sdk_limit = total`。

逐页结果由 `report.p_pages[0..page_count-1]` 提供：每页有 `write`、`read`
诊断及 `observed_page`。写入模式下，写失败仍然读取，但该页整体计为失败。
只读模式的写入结果是未执行，页面统计依据读取结果。
`page_match_count`、`page_failed_count`、`page_sdk_limit_count`、
`page_skipped_count` 之和等于 `page_count=36`。

逐页结果保存在模块静态区，**指针借用内容会在下次初始化或测试时更新**，
需要保存历史时由调用方另行复制；当前单次日志比较不需要增加 main 的栈数组。

厂家库和原始头文件保持原字节。可修改的平台层锁存每次库调用的首个错误，
后续成功不会覆盖，并记录实际 I2C 提交次数；每次库调用前清除记录。
因此库返回 0 不能掩盖底层失败，零次传输的边界拒绝也不能伪装成硬件探测。

硬件仍使用 PB6/SCL、PB7/SDA，开漏并需要外部上拉；软件 I2C 依赖 DWT
与 HAL 时基。日志使用已有 EasyLogger/RTT 通道 0。
用户源文件采用英文文件头和分区、中文函数与逻辑注释，不添加公司或个人字段。
